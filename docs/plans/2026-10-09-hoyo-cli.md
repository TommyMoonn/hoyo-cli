# HoYo CLI Implementation Plan

**Goal:** Build an installable, local-first `hoyo` command that displays fresh daily/weekly HoYoLAB status for Genshin Impact, Honkai: Star Rail, and Zenless Zone Zero, supports multiple accounts and explicit daily check-in, and falls back to clearly labeled recent cached status.

**Architecture:** Click routes commands into account/config and credential resolution, then a `genshin.py` gateway and game-specific adapters produce immutable application-owned status models. A status service handles concurrent requests, independent per-game cache fallback, and failure aggregation; Rich renders only those normalized models. Authentication, configuration, I/O, and rendering remain separate and mockable.

**Tech Stack:** Python 3.11+ (implementation choice, subject to the selected `genshin.py` version's compatibility), uv, Click, Rich, `genshin.py`, tomlkit, platformdirs, keyring, browser-cookie support compatible with `genshin.py`, pytest, pytest-asyncio, Ruff, and Pyright.

**Original plan:** [specs/implementation-plan.md](../../specs/implementation-plan.md). This repository copy uses the existing `specs/` paths. The original eight-phase plan defines implementation order.

**Source of truth:** The existing specification set (`README.md`, `scope.md`, `commands.md`, `data.md`, `design.md`, `config.md`, `auth.md`, `cache.md`, `errors.md`, `architecture.md`, and `testing.md`) and [implementation-plan.md](../../specs/implementation-plan.md) in the project's [spec directory](../../specs/README.md). See [commands](../../specs/commands.md), [architecture](../../specs/architecture.md), and [testing](../../specs/testing.md). Use its actual directory name; `specs/` below denotes the supplied layout. Read the specs in place and keep them unchanged.

## Global Constraints

- **Starting point:** The HoYo CLI project directory already exists and already contains the specification files. Work in that directory. Do not initialize another repository, recreate the project directory, move/extract the specs, or introduce separate working trees. Commits, if using Git, are optional manual checkpoints after passing tests; do not push automatically.
- Complete the **eight phases** of [specs/implementation-plan.md](../../specs/implementation-plan.md), starting with the missing project files (`.gitignore`, `.editorconfig`, `README.md`), followed by Python packaging, tooling, and CLI commands. The plan is for local use only, with no release/publishing/distribution workflow.
- Executable name: `hoyo`; game IDs: `genshin`, `hsr`, `zzz`; named accounts match **exactly**, without prefix matching.
- Status and config inspection are read-only with respect to HoYoLAB. Only `hoyo check-in` may claim rewards. Do not add automatic check-in, confirmations, `--json`, watch mode, or a persistent TUI.
- Every status invocation attempts the network first. Cached normalized status is **fallback only**, with a maximum age of **3 hours inclusive**. Never extrapolate regenerating resource amounts.
- Run requested games concurrently, keep failures independent, and preserve successful output. Status exits `0` if any requested game yields fresh or eligible stale status, otherwise nonzero; config failures use `2`, credential failures `3`, general/API failures `1`.
- Check-in exits `0` only if **all** requested games are claimed or already checked in. Partial outcomes must still be printed.
- Config: `~/.hoyo/config.toml`, schema `version = 1`; manually editable, comment-preserving, unknown-key-tolerant. Optional plaintext secrets: `~/.hoyo/credentials.toml`; never put secrets in normal config/output.
- Cache: use `platformdirs`-resolved OS cache root, isolated by account/game, envelope `cache_version = 1`. Cache writes succeed independently for each successfully fetched game.
- Rich uses semantic styles and game accents from `DESIGN.md`. Layout breakpoints are **wide >=80**, **medium 60-79**, **narrow <60** columns. Redirected output and `--no-color` are unstyled.
- Use `genshin.py` behind `hoyo_cli.hoyolab`; normalize immediately. No direct upstream classes in render/cache modules; no extra HTTP client unless the pinned library demonstrably cannot do an operation.
- The default test suite is fully mocked and offline; live tests are opt-in and read-only, and a live check-in is never part of automated verification.
- Normal CLI failures have concise messages without Python tracebacks. Keep the module boundaries in `ARCHITECTURE.md`; combine trivial modules only if the resulting responsibility stays cohesive.

## Review Focus

These five realistic failure modes supplement the spec's named acceptance scenarios; each is assigned a regression test below.

1. **Config write interruption or invalid existing TOML:** Preserve the original file byte-for-byte instead of partially replacing it (Tasks 6, 12).
2. **Multiple browsers, denied browser access, or user cancellation:** Never silently select another browser or leak pasted cookies (Tasks 10-11).
3. **Account has no enabled games or an explicit game is disabled/unconfigured:** Produce a useful nonzero error rather than a blank successful overview (Tasks 5, 21).
4. **Future-dated or incorrectly labeled cache entries:** Refuse them instead of displaying misleading stale/fresh status (Task 20).
5. **Interrupting an in-flight request:** End cleanly without a traceback or a retry of a cancelled operation (Task 14).
